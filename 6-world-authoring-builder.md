# World Authoring Builder + Viewer — implementation plan

## Purpose

Build a local production-authoring toolchain that combines:

- **THREE.Terrain** for exact-size procedural base terrain, deterministic seeds, smoothing, local terrain influences and lightweight sculpting;
- **Three.js Editor** for manual composition and asset placement;
- **Infuse guide objects** for roads, circular paths, rivers, rifts and other repetitive authored geometry;
- a deterministic **builder/exporter** that produces clean area/transition GLBs and validation reports;
- a local **authoring viewer** that previews the generated result at the same scale and transforms used by the game.

The user should spend time deciding **what the level should look like and where things belong**, not fighting terrain-generator scale limits, manually drawing curved road meshes, fixing UVs or repeatedly exporting chunks by hand.

This plan is self-contained. Read `AGENTS.md` and `three-editor.md` before implementation and follow all repository build/version/commit requirements.

---

## Core decision

For Areas 1-3, do **not** use Gaea or ProceduralTerrains as mandatory production dependencies.

Use `three.terrain.js` directly inside the Infuse authoring toolchain.

Reasons:

- it uses Three.js directly and supports Three r160+;
- Infuse currently uses Three 0.185.x, which is also the version used by the library's current demo/development setup;
- `xSize` and `ySize` are arbitrary Three.js units, so Area 1 can truly be 84 x 84 m;
- terrain resolution is independent from world size through `xSegments` / `ySegments`;
- min/max height can remain at small RPG-scale values rather than landscape-scale values;
- deterministic seeded generation is supported;
- built-in generators, smoothing and geographic influences cover the base-terrain needs;
- the library is MIT licensed;
- the current project includes a recent browser sculpting example that can inform the authoring viewer.

Do **not** copy the public THREE.Terrain demo UI unchanged. Its public size slider is tuned for large demo terrains and is not a library restriction.

## Desired user workflow

```text
1. Run:
   npm run authoring:viewer

2. In the viewer, create/tune the base terrain for A01/A02/A03:
   - exact visual dimensions
   - generator
   - seed
   - min/max height
   - frequency
   - smoothing
   - terrain influences
   - optional sculpting

3. Save terrain state locally under:
   authoring/local/terrain/

4. Run:
   npm run authoring:terrain-reference

5. Import the generated terrain reference GLBs into Three.js Editor when useful
   for composition, then place fountain, buildings, trees, rocks, walls,
   bridge and props manually.

6. Express roads/rivers/rings/rifts using simple GUIDE_* objects.

7. Export the Three.js Editor JSON to:
   authoring/local/three-editor/infuse-world.json

8. Run:
   npm run authoring:build

9. Inspect the assembled generated world in:
   npm run authoring:viewer

10. Iterate on terrain settings/sculpting, guides and manual placement.

11. Once satisfied, run:
    npm run authoring:promote

12. Commit only validated production GLBs + required runtime/code/data changes.
```

Important:

- the builder must **never mutate** `authoring/local/three-editor/infuse-world.json`;
- terrain state is saved separately so changing/sculpting terrain does not rewrite the Editor project;
- generated reference terrain imported into Three.js Editor is a **composition aid**, not terrain source-of-truth;
- final terrain is regenerated by the builder from the saved terrain state.

---

## Division of responsibility

### User / authoring viewer

Responsible for:

- choosing a terrain seed and broad terrain character;
- choosing exact small-scale elevation range;
- applying broad local terrain features/influences;
- sculpting only where procedural generation needs correction;
- visually checking chunk seams and terrain/road/river alignment.

### User / Three.js Editor

Responsible for:

- fountain/building/bridge/wall placement;
- tree, rock, vegetation and prop composition;
- broad road and river intent using GUIDE_* markers;
- visual storytelling and density;
- material/style references where the guide contract requires them.

### World-authoring builder

Responsible for:

- deterministic terrain generation from saved THREE.Terrain state;
- reapplying saved sculpt deltas;
- road/ring/river/rift geometry generation;
- UV generation and material cloning;
- placement/root transform validation;
- stripping authoring-only objects;
- independent area/transition GLB export;
- preview assembly;
- diagnostics and promotion.

### Infuse runtime

Responsible for:

- gameplay state;
- collision authority;
- area/transition streaming;
- explicit world placement;
- mobile rendering behavior.

Visual meshes remain non-authoritative for gameplay collision.

## Package dependency

Add the terrain library as a normal project dependency:

```bash
npm install three.terrain.js
```

Use its ES-module exports. Do not vendor/fork the library unless a concrete compatibility issue requires a small maintained patch.

Expected imports are conceptually:

```js
import Terrain, {
  TerrainNS,
  createSeededRandom,
} from 'three.terrain.js';
```

Do not depend on the library's demo application or dat.GUI implementation in production tooling. Reuse the library API and implement Infuse-specific controls in the authoring viewer.

Record the MIT dependency/license appropriately if the repository's release/license process requires it.

---

## Non-goals for v1

Do not expand the first implementation into a general-purpose landscape editor.

V1 does **not** require:

- Gaea integration;
- ProceduralTerrains integration;
- kilometer-scale terrain or world streaming inside THREE.Terrain;
- runtime procedural terrain generation;
- terrain LOD/geomipmapping;
- CSG/boolean union of road intersections;
- automatic vegetation scattering;
- automatic collision generation from visual meshes;
- automatic arbitrary-model decimation;
- a node-based terrain graph;
- a generic level editor replacement for Three.js Editor;
- multiplayer/cloud authoring storage;
- complex erosion simulation;
- automatic river-bank excavation in v1;
- automatic snapping/repositioning of arbitrary manually placed props to changed terrain.

Keep terrain amplitudes and iteration disciplined so large terrain changes do not constantly invalidate manual composition.

# Terrain subsystem

## Exact-size terrain requirement

THREE.Terrain world dimensions must use Infuse meters directly.

Current initial targets:

```text
A01 visual terrain: 84 x 84 m
A02 visual terrain: 96 x 84 m
A03 visual terrain: 96 x 84 m
```

Do not inherit the THREE.Terrain demo's 1024-unit defaults.

Conceptually:

```js
Terrain({
  xSize: 84,
  ySize: 84,
  xSegments: 63,
  ySegments: 63,
  minHeight: -0.5,
  maxHeight: 4,
  ...
});
```

Dimensions must come from the accepted Infuse visual-layout contract rather than duplicated arbitrary UI defaults.

The viewer can show the values but should not silently diverge from the accepted chunk dimensions.

---

## Terrain-state contract

Each terrain chunk has a local authoring file such as:

```text
authoring/local/terrain/a01.json
```

Suggested v1 shape:

```json
{
  "version": 1,
  "chunkId": "A01",
  "engine": "three.terrain",
  "generator": "PerlinDiamond",
  "seed": 123456789,
  "width": 84,
  "depth": 84,
  "xSegments": 63,
  "zSegments": 63,
  "minHeight": -0.25,
  "maxHeight": 3.5,
  "frequency": 1.4,
  "easing": "EaseInOut",
  "smoothing": {
    "type": "Gaussian",
    "strength": 0.5,
    "passes": 1
  },
  "edgePolicy": {
    "north": { "mode": "flatten", "height": 0, "distance": 5 },
    "east":  { "mode": "flatten", "height": 0, "distance": 5 },
    "south": { "mode": "free" },
    "west":  { "mode": "free" }
  },
  "influences": [],
  "sculpt": null
}
```

Exact names may change during implementation, but the saved schema must be versioned and validated.

### Why terrain state is separate from Editor JSON

- procedural terrain remains deterministic and easy to regenerate;
- sculpt data can change without rewriting a large Editor file;
- generated terrain references can be replaced safely;
- the builder does not need to treat an imported terrain mesh as authoritative source data;
- the user can experiment with terrain without corrupting manual asset placement.

---

## Supported generators in the first UI

Do not expose every THREE.Terrain algorithm on day one.

Start with a curated set suitable for small RPG areas:

```text
Perlin
PerlinDiamond
Simplex
DiamondSquare
Hill
HillIsland
```

`PerlinDiamond` can be the initial default if it gives a useful natural base.

Add more only when they provide a distinct authoring value.

---

## Terrain scale defaults

The viewer must default to **small game-level elevation**, not mountain-landscape values.

Suggested A01 starting ranges:

```text
width/depth     84 x 84 m
segments        63 x 63 initially
minHeight       around -0.25 to 0 m
maxHeight       around 2 to 4 m
frequency       low enough to create broad forms
steps           1
turbulence      off
stretch         evaluate; use intentionally
```

The user can raise west-border terrain with influences instead of asking the base random generator to produce mountains everywhere.

Do not expose 100-200 m default height amplitudes in the Infuse viewer.

---

## Deterministic randomness

Every terrain state must have an explicit 32-bit seed.

Use THREE.Terrain's seeded random helper where supported.

The same:

```text
terrain state
+ builder version
+ THREE.Terrain version
```

must reproduce the same pre-sculpt terrain.

The viewer needs:

```text
Seed [123456789] [New seed] [Regenerate]
```

Changing unrelated viewer settings must not implicitly randomize the terrain.

---

## Terrain influences

Use THREE.Terrain's influence system for deliberate broad terrain features rather than relying on pure noise.

Support a small explicit set in v1:

```text
Hill
Valley
Mesa
Hole
Dome
Flat
```

Each influence should save:

```json
{
  "id": "west-rise",
  "type": "Hill",
  "x": 0.08,
  "z": 0.5,
  "radius": 20,
  "height": 5,
  "blend": "additive",
  "falloff": "EaseInOut"
}
```

Viewer interaction should preferably allow selecting/dragging influence handles in world space rather than typing percentages manually.

Internally convert world X/Z to the normalized coordinates required by THREE.Terrain.

### Area 1 intended use

For A01, influences are particularly useful for:

- west elevated rock/cliff boundary;
- gentle localized rises around scenery;
- creating broad depressions that support the south rift composition;
- flattening a fountain plaza if necessary.

Do not use dozens of influences to hand-sculpt every meter. They are broad compositional controls.

---

## Edge policy and chunk seams

Independent procedural chunks can crack or visibly disagree at shared boundaries.

Do not solve this by returning to a giant Gaea-style master terrain in v1.

Instead implement explicit per-side edge policies.

Minimum modes:

```text
free
flatten
```

`flatten` blends terrain heights toward a shared Y over a configured distance from that side.

Example A01:

```text
north: flatten toward Y=0 for A01/A02 river transition
 east: flatten toward Y=0 for A01/A03 ruined-wall transition
south: free; the rift/rocks can form the outer boundary
 west: free; elevated terrain/rocks can form the outer boundary
```

The transition visual hides the intentionally controlled shared edge.

If future regions need seamless continuous natural terrain across many chunks, revisit a shared regional heightfield then. Do not add that complexity before it is necessary.

Validation must compare shared-edge heights for seams that are expected to match.

---

## Sculpting

Sculpting is part of v1 because it is the escape hatch when procedural generation is close but not quite right.

The viewer needs a deliberately small sculpt tool:

```text
Enable sculpt
Brush radius
Strength
Hardness/feathering
Raise
Lower
Optional flatten-to-height
Undo last stroke (at minimum)
Reset sculpt
Save terrain
```

Do not build Blender.

### Sculpt persistence

Do not require PNG decoding in the Node builder just to preserve sculpt work.

Store sculpted terrain changes as numeric data in the local terrain state.

Preferred implementation:

- regenerate deterministic base heights from the saved seed/settings;
- store a `sculptDelta` array matching the terrain vertex grid;
- final height = generated base + sculpt delta;
- omit/compact zero-only data when practical;
- validate array length against `(xSegments + 1) * (zSegments + 1)`.

For current terrain resolutions, a local ignored JSON array is acceptable.

A heightmap PNG export may be provided as a convenience/backup, but it should not be the only source required by the builder.

---

## Terrain materials

Do not make THREE.Terrain's legacy blended-material helper mandatory in v1.

Use a normal Three.js production material compatible with the rest of Infuse.

Preferred authoring contract:

```text
AUTHORING_GUIDES
└─ GUIDE_TERRAIN_STYLE
   └─ STYLE
```

The STYLE mesh provides the production terrain material to clone onto generated terrain.

For the first A01 proof, that can simply be a grass `MeshStandardMaterial` using:

```text
map
normalMap
roughnessMap
```

with repeat wrapping.

This keeps terrain generation independent from texture choice and avoids introducing a special terrain shader before it is needed.

If automatic slope/elevation texture blending later becomes clearly valuable, evaluate `generateBlendedMaterial()` or an Infuse-specific shader as a separate follow-up slice.

---

## Terrain-reference export for Three.js Editor

`npm run authoring:terrain-reference` generates lightweight reference GLBs from the exact same terrain generator used by the final builder:

```text
authoring/generated/editor-reference/terrain-a01.glb
...
```

Purpose:

- import the terrain into Three.js Editor;
- place fountain/buildings/rocks/bridge relative to its actual shape;
- avoid asking the user to imagine terrain while composing assets.

Reference terrain is disposable.

The final builder must not trust a stale imported terrain reference. It regenerates final terrain from `authoring/local/terrain/*.json`.

Use an unmistakable Editor name such as:

```text
REF_GENERATED_TERRAIN_A01
```

and strip it from shipping output so it cannot duplicate the builder-generated terrain.

If the terrain state changes materially after detailed asset placement, regenerate/reimport the reference before continuing composition.

## Input format support

The builder must accept JSON produced by the current Three.js Editor.

Support both:

1. a full Editor project containing a scene field;
2. an exported Three.js scene/object JSON document.

Detection must be explicit and errors useful.

Prefer Three.js `ObjectLoader` rather than manually reimplementing scene deserialization.

Handle embedded image data where supported. If source data contains unresolved external/blob URLs that cannot be loaded deterministically in Node, fail and identify the affected object/texture.

## Ownership rules

A guide belongs to the placement group containing it.

Examples:

- `GUIDE_ROAD_*` under `Placement_A01` generates into `Area_A01_Root`;
- the A01 terrain state generates into `Area_A01_Root`;
- `GUIDE_RIVER_*` under `Placement_Transition_A01_A02` generates into `Transition_A01_A02_River`.

Do not guess ownership from geometry overlap when hierarchy/config already defines it.

Manual production objects under shipping roots are preserved unchanged except for required chunk-export transform rebasing.

---

## Transform contract

Authoring:

```text
Placement_A02           world position (6,0,-72)
└─ Area_A02_Root        local position (0,0,0)
```

Shipping:

```text
Area_A02_Root           local position (0,0,0)
```

Runtime visual metadata owns `(6,0,-72)`.

Validate canonical shipping roots before export:

```text
position = 0,0,0
rotation = 0,0,0
scale    = 1,1,1
```

Do not silently bake incorrect shipping-root transforms.

Resolve nested guide point world transforms and convert them into owning shipping-root local coordinates before generation.

# Guide-generated geometry

## STYLE contract

Road/river/rift guides use a simple mesh named `STYLE` so the user does not need to edit material identifiers or widths in JSON.

For strip guides:

- compute STYLE world-space XZ bounds;
- smaller horizontal dimension = strip width;
- larger dimension = authored reference length for UV scale;
- clone STYLE material for generated output;
- STYLE never ships.

For `GUIDE_ROAD_RING_*`:

- derive inner/outer radii from ring-like STYLE geometry;
- fail clearly if reliable radii cannot be inferred.

`GUIDE_TERRAIN_STYLE/STYLE` provides the material only; terrain width/depth come from the authoritative terrain/layout state.

---

## Road ribbon generation

Given ordered `P_*` points:

- require at least 2;
- use `THREE.CatmullRomCurve3`;
- prefer centripetal/chordal behavior if more stable than uniform Catmull-Rom;
- preserve authored Y;
- sample around every 0.4-0.6 m with sensible clamps;
- generate left/right ribbon vertices from a horizontal perpendicular;
- use indexed triangles and consistent normals;
- tile UVs using cumulative path distance;
- use a centralized small surface offset to avoid terrain z-fighting.

### Terrain following

Roads should normally follow generated terrain rather than remain perfectly flat.

Add a builder utility that samples generated terrain height at X/Z.

For road points/samples where the authored Y does not intentionally override height:

```text
roadY = terrainHeight(x,z) + roadSurfaceOffset
```

Do not mutate source P_* objects.

Provide an explicit guide/userData override for roads that must preserve authored Y, such as a bridge approach.

This is important: once THREE.Terrain is integrated, generated roads must not disappear below small terrain undulations.

---

## Circular road generation

`GUIDE_ROAD_RING_*` generates a deterministic annular mesh around the landmark.

Requirements:

- smooth game-camera silhouette;
- cloned STYLE material;
- tiled UVs;
- terrain-height sampling around the ring where appropriate;
- small deterministic offset above terrain.

Do not implement CSG in v1.

Incoming road ribbons may overlap the ring slightly. Use a tiny deterministic offset difference only if needed to avoid z-fighting.

---

## River generation

Use the same centerline/ribbon foundation as roads.

V1:

- smooth centerline;
- STYLE-derived width/material;
- tiled UVs;
- deterministic geometry;
- transition-local output when owned by a transition;
- explicit water Y policy.

Do not automatically carve terrain banks in v1.

For A01/A02, the shared edge flattening and manually placed bank rocks/vegetation can hide the transition cleanly.

Bridge alignment remains visually authored and inspected in the viewer.

---

## Rift generation

A south-edge rift can be expressed with `GUIDE_RIFT_*` rather than requiring complex terrain sculpting.

V1 can generate:

- a dark recessed strip/ribbon;
- irregular-width edges derived from guide parameters or deterministic jitter;
- optional side-wall geometry;
- material cloned from STYLE;
- deterministic output.

Do not require boolean subtraction from the terrain mesh in v1. Visual overlap/recess plus rocks can sell the effect from the game camera.

---

# Builder pipeline

## Source safety

Never destructively modify source Editor scene data.

Recommended pipeline:

```text
load terrain states
load Editor scene
validate layout/roots/guides
        ↓
generate deterministic terrain objects
        ↓
extract normalized guide model
        ↓
clone each shipping root
        ↓
insert generated terrain into area clone
insert generated road/ring/river/rift geometry
        ↓
strip authoring-only/reference objects
        ↓
validate chunk-local transforms/materials
        ↓
export area/transition GLBs
        ↓
assemble preview from those same generated chunks
        ↓
write report + manifest
```

Repeated builds with unchanged inputs must not accumulate generated objects.

---

## Terrain insertion

For each area with terrain state:

1. generate exact-size THREE.Terrain geometry;
2. apply deterministic generator and seed;
3. apply configured smoothing;
4. apply edge policies;
5. apply authored influences in deterministic order;
6. apply saved sculpt deltas;
7. recompute normals/bounds;
8. assign cloned terrain STYLE material;
9. name output `GENERATED_TERRAIN_<id>`;
10. add it to the cloned canonical area root.

Centralize the order. Changing order changes terrain and must be treated as a builder-version change.

---

## Manual production geometry

Preserve manually authored production objects:

- buildings;
- fountain;
- trees;
- rocks/cliffs;
- walls;
- bridge;
- props;
- explicit production lights if convention allows them;
- manually authored special meshes.

Generated `REF_GENERATED_TERRAIN_*` objects imported for composition must be stripped to prevent duplicate surfaces.

Do not automatically move arbitrary manual objects vertically when terrain changes. Make such mismatches obvious in the preview instead.

A later opt-in `SNAP_TO_TERRAIN_*` convention can be added only if repeated manual adjustment becomes a real bottleneck.

---

## Authoring-only objects to strip

Before shipping export recursively remove:

- `Placement_*` wrappers;
- `AUTHORING_GUIDES`;
- `GAMEPLAY_GUIDES`;
- all `GUIDE_*` descendants;
- `REF_*` objects;
- `REF_GENERATED_TERRAIN_*`;
- STYLE objects;
- P_* markers;
- editor cameras/helpers;
- editor-only lights.

Production lights require an explicit convention.

---

## GLB export

Use Three.js `GLTFExporter` compatible with the project's Three.js version.

Implement a Node export spike using committed fixtures first.

If browser APIs are missing in Node:

- add the smallest local compatibility shim;
- keep it in `export/gltf-node-compat.mjs`;
- do not add a large exporter dependency unless the built-in exporter truly cannot work.

Export binary GLB.

Prefer self-contained GLBs initially where practical. Report asset duplication/file sizes so shared-resource strategy can be revisited with evidence.

# Authoring viewer

The viewer is no longer only a passive GLB viewer. It is the lightweight Infuse terrain-authoring surface.

## Viewer modes

Provide two clear modes/tabs:

```text
Terrain Authoring
Generated World Preview
```

### Terrain Authoring mode

Must provide:

- chunk selector A01/A02/A03;
- exact dimensions (displayed from layout contract);
- generator selector;
- seed + New Seed + Regenerate;
- min/max height;
- frequency;
- curated smoothing controls;
- influence handles/list;
- sculpt toggle and brush controls;
- reset sculpt;
- save terrain state;
- camera controls useful for top-down/isometric inspection;
- optional wireframe toggle;
- visible terrain bounds and playable-area reference;
- ability to load/reload terrain STYLE material if available.

Changes should update rapidly enough for interactive iteration on an 84-96 m chunk.

Do not regenerate on every tiny slider mousemove if that causes lag; use debouncing or regenerate on commit where necessary.

### Generated World Preview mode

Load `authoring/generated/preview/assembled-world.glb` and show:

- area/transition visibility toggles;
- guide/debug overlays when available from manifest;
- chunk bounds;
- production-style camera preset approximating Infuse portrait view;
- free/orbit camera;
- wireframe toggle;
- triangle/draw-call/texture counters where easy;
- terrain seam inspection;
- road/ring/river joins;
- manual object/terrain intersections.

The preview must use the same generated chunks exported by the builder, not a separate approximation path.

## Save behavior

Because `authoring/local/` is intentionally ignored, the browser viewer needs a practical local save/load flow.

Implement the simplest reliable option supported by the target browser/dev environment, for example:

- File System Access API when available; or
- explicit Download JSON / Load JSON controls as fallback.

Do not require a backend server just to save terrain state.

The UI must clearly show whether the current terrain has unsaved changes.

# Validation

`authoring:build` must fail on correctness problems rather than silently shipping bad art.

Minimum hard errors:

- missing required Editor source when building final chunks;
- malformed terrain-state schema;
- unknown terrain generator/easing/smoothing name;
- sculpt array length mismatch;
- non-finite terrain values;
- missing canonical shipping root;
- duplicate shipping root;
- bad root transform;
- ambiguous guide ownership;
- duplicate P_* indices;
- road/river with fewer than 2 points;
- invalid STYLE dimensions;
- unresolved required texture/image;
- output path collision;
- guide/reference object left inside shipping export.

Warnings may include:

- terrain amplitude unusually large for the chunk;
- very dense terrain segment count;
- manual object significantly below terrain surface;
- suspiciously large GLB;
- duplicate embedded texture cost;
- shared seam height mismatch within tolerance where matching is expected.

---

# Performance constraints

This is a mobile game; authoring convenience must not create runtime waste.

For the first A01 prototype:

- start around 63 x 63 terrain segments;
- only increase after viewing from the actual game camera;
- avoid dense runtime grass generated by THREE.Terrain in v1;
- use the existing Infuse asset/vegetation strategy for shipped decoration;
- avoid high-frequency terrain detail that is invisible at portrait camera scale;
- measure triangle count and GLB size;
- verify on the project's reference mobile constraints before promoting all areas.

THREE.Terrain's optional optimization modes are not a dependency of v1.

The terrain is authored/generated **offline**, then shipped as normal static geometry. Do not run procedural terrain generation on the player's device.

# Acceptance criteria

The implementation is successful when all of the following are true:

1. Area 1 terrain is generated at exactly **84 x 84 m** without external terrain tools.
2. The same terrain state produces the same base terrain on repeated builds.
3. The viewer can generate a useful low-amplitude RPG terrain with only a handful of controls.
4. Broad features can be deliberately shaped with influences.
5. Sculpt corrections persist and replay deterministically.
6. The user can import a generated terrain reference into Three.js Editor for composition.
7. A few crude `P_*` markers generate a smooth dirt road.
8. A ring guide generates a circular road around the fountain.
9. Roads follow terrain height instead of clipping through it.
10. River/rift visuals can be generated without Gaea/ProceduralTerrains.
11. Manually placed assets remain under the user's control and are not silently repositioned.
12. Generated references/guides never ship.
13. Area/transition shipping roots remain local `(0,0,0)`.
14. Preview assembly uses the exact chunks that would be promoted.
15. Production assets are only copied to `public/assets/world/` after validation.
16. The first mobile proof stays within Infuse performance/payload constraints.

---

## Final architectural rule

The authoring stack should remain:

```text
THREE.Terrain
  = quick exact-size base terrain + influences + sculpt

Three.js Editor
  = composition + asset placement + guide placement

Infuse world-authoring builder
  = deterministic regeneration + roads/rivers/rifts + validation + export

Infuse runtime
  = static shipped GLBs + explicit transforms + gameplay authority
```

Do not turn THREE.Terrain into a runtime world system and do not turn Three.js Editor into a hand-modelling requirement. The goal is to keep the user's work visual and high-level while Codex owns the repetitive geometry and export mechanics.
